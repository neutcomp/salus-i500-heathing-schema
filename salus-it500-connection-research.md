# Salus iT500 connection: static-source findings

**Scope.** Static review only of `RichyA/pyit500` at commit [`a1adfa516a9930e487c740f4e1fa114d323ff2c9`](https://github.com/RichyA/pyit500/tree/a1adfa516a9930e487c740f4e1fa114d323ff2c9). No Salus service was contacted, and no credentials or secrets were used. This is an unofficial Python client; its README describes it as a library for a Home Assistant integration ([README](https://github.com/RichyA/pyit500/blob/a1adfa516a9930e487c740f4e1fa114d323ff2c9/README.md)).

## What the source does

- **Host and transport:** The source specifies the HTTPS host `sal-emea-p01-api.arrayent.com` and constructs API URLs from that host and an internal API path ([`auth.py`, lines 9–11, 63–66](https://github.com/RichyA/pyit500/blob/a1adfa516a9930e487c740f4e1fa114d323ff2c9/src/pyit500/auth.py#L9-L11)). It does not add custom HTTP headers; it forwards the request arguments to `aiohttp` ([`auth.py`, lines 43–67](https://github.com/RichyA/pyit500/blob/a1adfa516a9930e487c740f4e1fa114d323ff2c9/src/pyit500/auth.py#L43-L67)).
- **Authentication/session:** The caller supplies an `aiohttp.ClientSession`, username, and password. The code computes an unsalted MD5 hex digest of the password, POSTs JSON containing the username and digest to its session-creation route, then reads a user ID and security token from the JSON response into the `Auth` instance ([`auth.py`, lines 2–3, 13–27, 33–41](https://github.com/RichyA/pyit500/blob/a1adfa516a9930e487c740f4e1fa114d323ff2c9/src/pyit500/auth.py#L2-L3)).
- **Subsequent requests:** The wrapper adds the stored token and user identifier to request data for POSTs or query parameters for other methods; it adds no custom authentication header ([`auth.py`, lines 43–67](https://github.com/RichyA/pyit500/blob/a1adfa516a9930e487c740f4e1fa114d323ff2c9/src/pyit500/auth.py#L43-L67)). For safety, this note does not reproduce the exact route strings or parameter keys.
- **Read/control flow:** The client can retrieve a device list and user/device attributes, parsing XML responses with `xmltodict` ([`devicelistitem.py`, lines 17–27](https://github.com/RichyA/pyit500/blob/a1adfa516a9930e487c740f4e1fa114d323ff2c9/src/pyit500/devicelistitem.py#L17-L27); [`user.py`, lines 43–55](https://github.com/RichyA/pyit500/blob/a1adfa516a9930e487c740f4e1fa114d323ff2c9/src/pyit500/user.py#L43-L55); [`device.py`, lines 161–171](https://github.com/RichyA/pyit500/blob/a1adfa516a9930e487c740f4e1fa114d323ff2c9/src/pyit500/device.py#L161-L171)). It also implements device writes: a GET request carries device and attribute/value data, after which the code schedules an attribute refresh ([`device.py`, lines 132–159](https://github.com/RichyA/pyit500/blob/a1adfa516a9930e487c740f4e1fa114d323ff2c9/src/pyit500/device.py#L132-L159)). Zone setters delegate to that device control path ([`zone.py`, lines 56–72](https://github.com/RichyA/pyit500/blob/a1adfa516a9930e487c740f4e1fa114d323ff2c9/src/pyit500/zone.py#L56-L72)).
- **Token lifecycle / implementation caveats:** The token is held in memory on the `Auth` object; the public wrapper exposes an explicit session refresh method ([`auth.py`, lines 21–27, 33–41](https://github.com/RichyA/pyit500/blob/a1adfa516a9930e487c740f4e1fa114d323ff2c9/src/pyit500/auth.py#L21-L27); [`pyit500.py`, lines 16–22](https://github.com/RichyA/pyit500/blob/a1adfa516a9930e487c740f4e1fa114d323ff2c9/src/pyit500/pyit500.py#L16-L22)). There is no visible expiry handling or automatic refresh/retry logic in these paths. Also, `Auth.__init__` calls the asynchronous refresh method without awaiting it when `get_token=True`, so that option does not itself wait for authentication to finish ([`auth.py`, lines 13–27](https://github.com/RichyA/pyit500/blob/a1adfa516a9930e487c740f4e1fa114d323ff2c9/src/pyit500/auth.py#L13-L27)). The login method also does not call `raise_for_status()` before parsing its response, unlike the read/write methods ([`auth.py`, lines 33–41](https://github.com/RichyA/pyit500/blob/a1adfa516a9930e487c740f4e1fa114d323ff2c9/src/pyit500/auth.py#L33-L41); [`device.py`, lines 150–171](https://github.com/RichyA/pyit500/blob/a1adfa516a9930e487c740f4e1fa114d323ff2c9/src/pyit500/device.py#L150-L171)).

## Dependencies and WordPress adaptation

The implementation imports `aiohttp` for HTTP sessions/responses and `xmltodict` for XML parsing; hashing and async timing/task support come from Python’s standard library ([`auth.py`, lines 2–3](https://github.com/RichyA/pyit500/blob/a1adfa516a9930e487c740f4e1fa114d323ff2c9/src/pyit500/auth.py#L2-L3); [`device.py`, lines 2–11](https://github.com/RichyA/pyit500/blob/a1adfa516a9930e487c740f4e1fa114d323ff2c9/src/pyit500/device.py#L2-L11)).

For a WordPress port, treat this as an undocumented, stateful cloud protocol rather than a drop-in API: PHP/WordPress needs its own HTTP, response/XML parsing, timeout, and error-handling flow; protect account credentials and session tokens server-side; and gate every state-changing action behind authenticated, authorized WordPress controls. Do not carry over the unsalted-MD5 password transformation as a general security pattern. The source does not establish vendor support, protocol stability, or authorization to use the service.

**Identity-tool limitation:** `github/get_me` was not exposed in this environment, so repository access was performed against the public source without an authenticated identity check.
